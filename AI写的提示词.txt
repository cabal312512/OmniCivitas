你现在要从头实现一个完整的恶搞网站项目。

在开始写代码之前，先完整阅读仓库中的 `PROJECT_SPEC.txt`。这个文件是本项目最重要的规格说明，其中已经详细列出了技术栈、架构、代码风格、数据库设计、前端交互、故意糟糕的设计、网站功能、视觉表现以及各种异常行为。不要跳读，也不要擅自把里面那些明显不合理的设计“优化”掉。

项目的核心设定是：

这是一个自称“超级无敌万能网站 / 人类文明技术结晶”的平台，号称能够解决几乎一切问题。它集成了大量完全没有必要同时使用的技术、框架、数据库、协议和历史遗留代码。网站内部拥有大量彼此毫无关系的功能，同时存在非常混乱、丑陋、反直觉、令人困惑甚至看起来像坏掉了的 UI 和交互。

它不是一个正常项目。

这个项目的笑点来自两个方向：

1. 对用户而言，它应该像一个规模巨大、历史悠久、由无数互不沟通的团队拼起来的平台。界面风格混乱，导航逻辑诡异，控件行为反直觉，有大量看起来像 Bug 的故意设计，并且经常出现完全不必要的流程、提示、动画和页面跳转。

2. 对程序员而言，源码应该充满极其糟糕的架构决策、重复实现、多余依赖、错误抽象、历史遗留代码、复制粘贴、奇怪命名、无意义兼容层、多种技术同时解决同一个问题等内容。

但是有一个非常重要的原则：

“设计很烂”和“程序真的坏了”是两回事。

网站必须能够真正安装、启动、构建和使用。主要页面不能随机白屏，主要功能不能因为真正的死循环、内存泄漏、数据库损坏、无限重定向等问题无法完成。

规格文件中那些看起来像浏览器卡死、无限加载、按钮逃跑、错误页面、失败请求、随机异常等效果，原则上都应该用可控、有限、可恢复的方式模拟，而不是故意真正破坏浏览器或服务器。

优先级从高到低如下：

1. 项目可以稳定安装、启动、构建。
2. 用户主要流程能够完成。
3. 严格保留 `PROJECT_SPEC.txt` 中规定的荒谬设计和技术债。
4. 尽量实现其中列出的功能。
5. 最后才考虑正常软件工程中的“优雅”“统一”“简洁”。

所以请不要看到重复代码就主动重构，不要看到多套框架就统一成一个框架，不要看到无用依赖就全部删除，不要看到奇怪数据库设计就重新设计成正常 schema。

这些东西很多就是项目本身的一部分。

但是基础设施层面仍然应该可靠，例如：

- 项目启动脚本
- Docker / Compose 配置
- 数据库初始化
- migration
- 必要的错误恢复
- 请求超时
- 输入长度限制
- HTML 转义
- SQL 参数化
- 文件处理边界
- 主流程测试
- 防止真正无限循环
- 防止真正无限递归
- 防止真正内存爆炸
- 防止不可恢复的数据损坏

这些不要故意写坏。

本项目没有真实用户系统，也不要收集、保存或处理真实密码、真实个人信息或真实敏感数据。规格文件中涉及注册、登录、账户、密码、身份等内容，全部按照恶搞/虚构身份机制实现。

对于功能实现复杂度，遵循以下原则：

简单功能：
直接实现。

中等复杂功能：
优先使用成熟依赖，不要浪费大量代码自己重新实现标准算法。

复杂但并不重要的功能：
只实现合理的演示版、简化版或者模拟结果。

非常复杂且只是为了丰富网站入口的功能：
允许只有完整 UI 和少量假逻辑，也允许根据规格文件故意跳转到别的模块、返回固定数据、显示维护提示或采用荒谬 fallback。

不要为了一个边缘小功能写几百上千行复杂算法。

这个项目追求的是“大量东西同时存在”，而不是每一个功能都达到生产级质量。

实现时请尽量让不同模块体现出像不同年代、不同开发团队、不同公司写出来的感觉。不要试图建立统一设计系统。不同页面可以拥有不同布局、组件体系、代码习惯、接口风格和视觉语言。

规格文件里指定需要混用的技术，请真的尽量使用，而不是只把依赖写进 package.json。

但也不要求每一种技术承担大量业务。一些技术只负责一个很小、完全没有必要单独使用它的功能，反而更符合项目目标。

对于仓库中那些故意存在的旧项目、无关代码、历史配置、错误命名和死代码：

不要为了“清理代码”删除它们。

其中一部分可以完全没有使用，一部分可以只被非常荒谬地复用一次，一部分只是作为历史遗迹存在。

如果需要新增这种内容，请原创模拟“从另一个项目复制过来忘记清理”的效果，不要直接复制未知第三方项目的大量源码。

代码可以故意非常难看，例如重复、硬编码、错误抽象、复制粘贴、奇怪变量名、过度包装、多余转换和历史兼容层。

但不要通过以下方式制造“烂代码”：

- 真正无限循环
- 真正无限递归
- 故意制造严重内存泄漏
- 随机破坏数据库
- 不可恢复的 race condition
- 真正锁死浏览器
- 任意执行用户输入
- SQL 注入
- XSS
- 路径穿越
- 无限制上传
- 真实凭证泄漏
- 其他会让这个玩具网站变成安全事故的行为

如果“故意写烂”和“网站能稳定运行”发生冲突，以稳定运行优先，然后想办法用更可控的方式制造同样的荒谬效果。

实现顺序不要完全按照规格文件从第一条机械做到最后一条。

先建立一个可以运行的总体骨架，然后逐步往里面塞东西。


不要因为测试失败就把故意的异常 UI 和奇怪行为删掉。测试应该区分“预期的恶心行为”和“真正的程序错误”。

你可以自行添加、安装和配置依赖。

如果某项规格在当前技术条件下完全不现实，先采用最接近原意、同时能稳定工作的方式实现，并在项目中的开发记录里注明，而不是直接删除这个点。

如果规格中的两条要求互相冲突，按照下面顺序判断：

可运行性 > 明确写出的项目设定 > 恶搞效果 > 技术完整度 > 正常的软件工程最佳实践。




最终目标不是做一个“看起来故意很烂的 Demo”。

最终目标是做出一个真的拥有大量页面、大量功能、大量技术、大量历史包袱，而且居然还能正常运行的巨大怪物网站。

当一个程序员打开仓库时，他应该不断产生“为什么这里会有这个”的疑问。

当普通用户打开网站时，他应该不断产生“为什么网站要这样”的疑问。

但是两个人最后都应该发现：

它居然真的能用。
